IMPLEMENTATION PLAN — READ BEFORE HANDING TO A CODING AGENT

Wanderbricks NL-to-SQL Agent

A chat interface, backed by a FastAPI agent, that turns questions about the Wanderbricks Delta Lake tables into SQL and answers them — built as a first hands-on project in retrieval, tool use, and Databricks integration.

00What you're actually building

A chatbot that turns natural-language questions into SQL, runs that SQL against Databricks Delta tables, and answers using the results. This pattern is NL-to-SQL with schema-aware RAG. It is not RAG over documents — you are not embedding rows of data. You are embedding metadata (table and column descriptions, relationships, sample values) so the LLM knows what it's allowed to query and how the tables relate, before it ever writes SQL.

Three concepts this project is designed to teach, in order: (1) building and querying a small vector index — the "retrieval" half of RAG; (2) safely turning free text into SQL and executing it against a real warehouse — tool use, not just chat; (3) wiring a stateless FastAPI backend to a React chat frontend.

Keep every piece boring and inspectable at first. Swap in production-grade tools later — see Section 08.

03Component-by-component plan

3.1  Databricks access layer

Create a Databricks SQL Warehouse (serverless is fine for a demo) with access to the wanderbricks catalog/schema. Create a personal access token, or — better for anything beyond your own laptop — a service principal with SELECT on the wanderbricks schema only, nothing else. This is your first real production-readiness decision: the agent's DB credential should be as narrowly scoped as possible, because the LLM is going to be writing arbitrary SQL with it.

Two ways to talk to Databricks at runtime — pick one:

OptionNotes
databricks-sql-connectorSimplest — feels like any DB-API driver. Fastest way to get moving.
Statement Execution REST APIWhat you called "SQL API endpoints." More architecturally honest for a service — stateless HTTP, poll for statement completion, parse JSON result chunks. Recommended once the connector version works, for the learning value.

3.2  Ingestion pipeline build this first

Produces one document per table describing: name and purpose, each column's name/type/description, known join keys, and 2–3 example rows or distinct categorical values (helps the LLM write correct WHERE clauses instead of guessing, e.g. knowing status is 'confirmed'|'cancelled'|'pending').

  1. Script that runs DESCRIBE TABLE EXTENDED <table> for each of the 9 tables, plus SELECT * LIMIT 5 for sampling.
  2. Hand-author (or LLM-generate once, then review) a plain-English description per table and column — the single highest-value step for query accuracy, worth doing by hand at 9 tables.
  3. Chunk per table, not per column — one embeddable document per table, since questions usually need "all context about table X."
  4. Embed each document (e.g. OpenAI text-embedding-3-small) into a local vector store — chromadb in embedded mode is enough at this scale, and teaches you the real interface without running a server.
  5. Persist the index to disk so FastAPI loads it at startup instead of rebuilding per request.

Output: a metadata_index/ folder (Chroma persistence dir) plus the raw JSON descriptions — keep the JSON, you'll read it directly when debugging bad SQL.

3.3  FastAPI backend — the agent loop

One endpoint, POST /chat. On each call:

  1. Retrieve — embed the question, similarity-search the metadata index, pull the top 3–5 most relevant table documents.
  2. Generate SQL — call the LLM with only the retrieved schemas (not all 9 — that's the point of retrieval) and the question. Ask for SQL only.
  3. Guardrail before running — reject anything that isn't a single SELECT, enforce a LIMIT, whitelist table names, set a timeout.
  4. Execute — run via the connector/API, catch errors, and on a SQL error feed it back to the LLM for one or two repair attempts.
  5. Summarize — call the LLM again with the question and result rows (cap rows fed back, e.g. 50) for a natural-language answer.
  6. Return — JSON with the answer, plus the generated SQL and retrieved table names, so the UI can show "how I got this answer."

Keep the agent stateless per request at first — pass full chat history from the frontend rather than server-side session storage. Simpler to reason about, and a fine production pattern too for v1.

3.4  React frontend

One chat window: message list + input box. POST the running history to /chat on submit, render the answer, optionally render the generated SQL in a collapsible block — useful while building, and trust-building for real users later. No auth, no persistence, no token streaming for v1; add streaming only once the basic request/response loop works end to end.

04Build order

Follow this sequence, not the architecture diagram top-down. Resist building frontend and backend in parallel — most of your early time goes into prompt/SQL quality, which is far faster to iterate on from a terminal script than through a browser.

  • Databricks connectivity smoke test. A standalone script that connects and runs SELECT * FROM wanderbricks.bookings LIMIT 5. Don't touch AI or FastAPI until this works.
  • Manual schema description pass. Hand-write the JSON descriptions for all 9 tables. Data entry, not coding — but it determines whether your SQL generation is any good.
  • Ingestion script. Embed the JSON, write to a local Chroma store. Verify by embedding a test question ("which host had the most bookings?") and confirming the top 3 retrieved tables are bookings, hosts, properties — not clickstream.
  • NL→SQL script, no FastAPI yet. Hardcode a question, retrieve context, call the LLM, print the SQL. Iterate on the system prompt here — most debugging time goes here.
  • Add execution + guardrails to the same script. Run the generated SQL, print results.
  • Add the summarization call. Full pipeline now works end-to-end from a terminal.
  • Wrap it in FastAPI. Move the working script logic into /chat. Test with curl/Postman before touching React.
  • Build the React chat UI against the working API.
  • Add the error-retry loop, request logging, and the "show me the SQL" UI toggle.

05Prompting notes specific to this project

The NL→SQL system prompt should include: the retrieved table schemas (name, columns, types, join keys, sample values), the target dialect — Databricks SQL / Spark SQL has quirks vs. standard SQL, e.g. date functions — and an explicit instruction to use only the provided tables and columns.

Ask for SQL in a fenced block with a fixed tag (```sql) so parsing it out is a simple regex, not free-text parsing. For the summarization call, cap the number of result rows fed back (e.g. first 50) rather than dumping an unbounded result set into the prompt.

06Minimum guardrails checklist

Don't skip these for a "just learning" project — the LLM is writing SQL that actually executes.

  • Read-only DB credential, enforced at the Unity Catalog permission level, not just in Python.
  • Reject non-SELECT statements before execution.
  • Reject multiple statements / statement chaining.
  • Enforce a row LIMIT.
  • Enforce a query timeout.
  • Table/column whitelist check against the known 9 tables.
  • Log every generated SQL statement with the question that produced it — invaluable for debugging, and later for an eval set.

08Path to production

Read after v1 works — don't build this now. Roughly in order of value:

  1. Evaluation set — 15–20 question/expected-SQL pairs to catch regressions when prompts change.
  2. Semantic layer instead of raw schema dump — curated views reduce join-guessing surface.
  3. Streaming responses in FastAPI (SSE) and React.
  4. Session/conversation persistence (Postgres/Redis) instead of client-passed history.
  5. Auth in front of both the React app and FastAPI.
  6. Swap local Chroma for a managed vector store if the metadata catalog grows past what fits in memory.
  7. Observability — log latency and token cost per stage: retrieval, SQL-gen, execution, summarization.

09What to hand to a coding agent next

Once you're comfortable with this plan, hand it off as separate, sequential tickets matching Section 04's build order — e.g. "Ticket 1: Databricks connectivity smoke test script" — rather than one "build the whole thing" prompt. Easier for you to review and learn from each piece, and easier for the agent to get right.
